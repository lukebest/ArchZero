# 2608.30509: CHIPSMORE: Compute-in-Interconnect and -Memory Chiplets for Multi-Mode Multi-Request LLM Inference Acceleration

- arXiv: [2608.30509](https://arxiv.org/abs/2608.30509) · PDF: [arxiv.org/pdf/2608.30509](https://arxiv.org/pdf/2608.30509)
- Venue: none stated (IEEE journal-style preprint, v1 31 Aug 2026; cs.AR). 13 PDF pages.
- Domain tag: LLM decode / NoC
- One-line hardware fact: chiplet mesh of heterogeneous RRAM-ACIM + SRAM-DCIM PEs whose 2D-mesh routers also do DMAC, with KV spilled across scratchpad / SRAM-DCIM / 2T0C eDRAM, and a layer-pipeline that shares one RRAM weight copy across batched requests.
- Lab note: same NUS ECE group (Chong, Wang, Fong, et al.) as LEAP ([2609.00857](2609.00857.md)). CHIPSMORE *adopts* LEAP’s spatial mapping (p.6, ref. [29]) and shares the IMC+in-network-compute fabric. Treat as a sequel, not an independent lab.

## 四视角独立批评

### 微架构

Strip the “orchestration framework.” The hardware is a persistence split plus a programmable mesh.

**Structures.** Each PE is a pair of CIM macros: RRAM-ACIM 256×256 for frozen pretrained weights (analog MVM, cite Wan *Nature* 2022 [25]); SRAM-DCIM 256×64 for LoRA / optional KV (digital MAC, cite Chih ISSCC 2021 [26]) (p.3–4, Table III p.7). Each unit router has N/S/E/W ports with 256 B FIFOs, a pair of AXI-Stream adapters into the two macros, a command-decoder FSM, a scratchpad, and **seven computational macros** (partial sum, activation, DMAC) feeding a 4×7 output crossbar (Fig. 3, p.4). The paper’s vocabulary: SMAC = MAC on static weights inside the CIM arrays; DMAC = MAC on runtime tensors *inside the router* (Q·Kᵀ is the running example) (p.3). That is the mechanism. “Compute-in-interconnect” is DMAC-in-router, not magic in the UCIe PHY.

Control plane: Network Program Memory with double-buffered Bank1/Bank2, each holding CMD and Config registers; a Configuration Co-processor DMA’s the next program from system memory while the other bank runs; a Network Main Controller walks a 30-bit ISA (Fig. 3 bitfields: `sp_addr`, `wr_en`, `intxfer_en`, `out_en`, `mode_sel`, `rd_en`) and a 64-bit CMD pair plus a config word with repeat count and per-router CMD1/CMD2/IDLE select (p.4–5). That is a VLIW-ish SIMD mesh, centrally sequenced. Not adaptive routing. Not a cache-coherent NoC.

Capacity hierarchy (Table III, p.7): per compute tile (CT), 32×32 IPCN, 16 MiB scratchpad, 16 MiB SRAM-DCIM, 64 MiB 2T0C eDRAM (refresh 10 ms, non-destructive read [27]), 2× UCIe endpoints × 16 lanes, 1 GHz, 64-bit, 7 nm, cluster size 4 chiplets. KV policy (Table II, p.6): Base mode walks scratchpad → SRAM-DCIM → eDRAM; LoRA *reserves* SRAM-DCIM for adapters and walks scratchpad → eDRAM. Overflow stripes onto adjacent chiplets (p.7). That is a software allocator over three SRAMs and an eDRAM, not a hardware cache with tags.

Multi-request “pipeline” (Fig. 4, p.6): each transformer layer is *statically* bound to a unique weight-bearing CT cluster. Requests are injected at temporal offsets so they occupy different layers at once. Weights are not replicated. A stage has exclusive occupancy — one request per layer at a time (p.8). That is software pipeline scheduling on a spatially unrolled model, not a hardware scoreboard.

Power gating (p.7): after a layer finishes, keep RRAM (nonvolatile, can go dark), keep whatever SRAM/eDRAM holds LoRA or KV, gate IPCN and idle compute. Policy, not a new retention bitcell.

**Mechanism vs policy.** Mechanism: heterogeneous PE, DMAC router macros, 30-bit ISA, 2T0C eDRAM, UCIe endpoints, layer-static spatial map inherited from LEAP/PRIMAL (p.6). Policy: rectangular column-wise weight placement, mode-dependent KV waterfill, request offset into the layer pipeline, which clusters stay powered. Unified spatial mapping is explicitly *not new here* (p.6).

**What the reverse-engineer wants and does not get.** Analog RRAM: no conductance levels, no ADC/DAC energy, no IR-drop, no write-verify, no endurance budget for the one-time program. SRAM-DCIM 256×64 vs. RRAM 256×256: how LoRA ranks sit on that aspect ratio is “same geometric decomposition” (p.6) — a sentence, not a floorplan. Router “×7 computational macros” are boxes. eDRAM is a citation to an IGZO 2T0C ESSERC 2025 cell paper [27], not an array compiler. 32×32 mesh at 1 GHz with a *central* NMC is a control-radius problem they do not discuss.

### 负载

They advertise “multi-mode multi-request” and then run a 3×3×3 cube: models Llama 3.2-1B / Mistral-7B / Qwen3-14B, contexts S/L/XL = 2048/2048, 4096/4096, 8192/8192, batches 1/2/4, INT8 weights, LoRA rank-8 on Q and V only (p.7–9, Table IV). That is not “diverse LLM serving.” That is a design-of-experiments over the knobs their allocator already knows.

What actually stresses the paper: decode underutilization with one token/request (Fig. 1, p.1; p.2); KV bytes `B T L (2 N_KV d_head) b_KV / 8` (Eq. 1, p.2); LoRA stealing the SRAM-DCIM tier so KV falls into eDRAM (Fig. 6, p.8; Table IV). Those three are real. The XL point is the only one that forces eDRAM (64 MiB/layer, p.9). Short context never leaves the scratchpad. So most of the “hierarchical KV” story is idle silicon.

What is missing. No MoE (Mistral-7B is run as if it were a dense 7B for the H100 table — they never mention experts). No continuous batching, no paged KV, no heterogeneous sequence lengths in a batch (Fig. 4 draws four identical rectangles). No arrival process. No speculative decoding. No context past 8k. No prefill-only vs. decode-only split of the headline tokens/s (Table V, p.12, is one number for “base-mode long context 4096/4096”). No quality metric of any kind — this is a throughput/power paper on INT8 as if INT8 were free accuracy.

Baseline fairness is the usual CIM-vs-GPU crime. Table V: H100 + vLLM at 350 W / 467 tokens/s (B=1) vs. CHIPSMORE 30.7 W / 1112.5 tokens/s. Apple M4-Max, Cerebras-2 at 18 kW, CENT, H2-LLM, CHIME. Different nodes, different precision stories, different whether weights are on HBM or “already programmed into RRAM.” The 27× tokens/J is 36.24 / 1.34 (p.12). A workload reviewer will not accept “H100 is the baseline” when the workload is a homogeneous batch of 4096/4096 Mistral-7B-INT8 with no sampling, no MoE, and no KV offload to HBM because they assumed the model *fits in RRAM*.

Pipeline-depth vs. batch is the only honest workload graph: Llama-1B (16 layers) fills at B=4; Mistral-7B (32 layers) does not (Fig. 7, p.9–10). They buried the implication: *replication-free* throughput is bounded by `min(batch, pipeline_depth)` and exclusive stages. That is Amdahl on a 32-stage pipe with 4 in-flight requests. Not a serving system.

### 仿真方法学

“Cycle-accurate hardware–software co-simulation” (abstract) unpacks to (p.7): Verilog of the *digital* pieces, Synopsys DC at 7 nm, CACTI for scratchpad, a cycle-accurate *instruction-level* simulator of the IPCN ISA plus LEAP/PRIMAL mapping [18], [29]. RRAM-ACIM numbers are from a 2022 Nature chip [25]. SRAM-DCIM from a 22 nm ISSCC macro [26] dropped into a 7 nm table. eDRAM from an IGZO 2T0C paper [27]. UCIe is a spec citation [28]. There is no chiplet package model, no interposer trace, no RRAM variation Monte Carlo, no 10 ms refresh traffic in the throughput graphs (refresh is a table footnote).

Energy: Fig. 10 (p.11) reports average power as total energy / time, which is why long context can *lower* average watts while burning more joules — they say this out loud (p.11). Good. Tokens/J in Table V still gets compared to a 350 W GPU nameplate. Area is one pie chart (Fig. 11, p.11: 32.0 / 37.1 / 17.5 / 8.9 / 3.7 / 0.8 %) with no legend in the extractable text — the paper never gives mm² for a CT or for a 14B system.

What was not measured: silicon; analog MVM accuracy vs. INT8; UCIe latency under contention (they report utilization <25% at B=4, p.11, and conclude the fabric is not the bottleneck — a simulator that localizes traffic by construction will say that); power-gate wake-up; eDRAM retention fails; compiler/API cost of the “toolchain” (p.5). The H100 numbers are a literature / datasheet bake-off, not a vLLM run they describe.

A tools reviewer notes the methodological incest: the simulator “implements the IPCN instruction set along with the proposed mapping and dataflow schemes [18], [29]” (p.7). That is the same group’s LEAP/PRIMAL model. CHIPSMORE’s speedups are not an independent reproduction of LEAP; they are LEAP’s engine with more memory boxes.

### 工业可行性

This is a research fabric that assumes the hard analog and packaging problems are already solved by the citations.

To stand up Mistral-7B or Qwen3-14B you need enough 256×256 RRAM macros to hold INT8 weights *plus* the unused replica you proudly did not build. Programming analog RRAM at scale (write energy, verify, stuck-at, drift, temperature) is not in the paper. Endurance is why they refuse to put KV in RRAM (p.1) — then they still need a one-time load from “Sys. Main Memory” (Fig. 3). SRAM-DCIM at 16 MiB/CT plus 16 MiB scratch plus 64 MiB eDRAM, times a 32×32 mesh of PE-pairs, times 4 chiplets, times enough clusters for 14B, is an area number they never write down. Fig. 11’s pie without a denominator is not an area claim.

7 nm DC of the digital mesh + CACTI SRAMs + a 22 nm SRAM-CIM paper + a Nature RRAM chip + IGZO eDRAM is four process fairy tales in one table (Table III). UCIe 16-lane endpoints with <25% utilization (p.11) means they overprovisioned the one industry-standard thing in the drawing.

Software: a custom 30-bit mesh ISA, a compiler/API (p.5), a runtime that must (a) place rectangular weight tiles, (b) waterfill KV by mode, (c) stagger requests into a layer pipeline, (d) power-gate around volatile state. There is no PyTorch, no vLLM block manager, no tokenizer path. LoRA is rank-8 on Q and V (p.9) — not a serving LoRA multiplexer with dozens of adapters.

What breaks in a real SoC: analog CIM vs. the INT8 accuracy they never measured; exclusive layer stages so a 80-layer model at B=4 is mostly powered SRAM/eDRAM holding KV (they *call* this a feature, p.7, p.10); eDRAM 10 ms refresh vs. decode ITL; 32×32 centralized command distribution at 1 GHz; yield of analog arrays at chiplet volume; the fact that “no weight replication” just moves the replica problem into *time* (pipeline depth) and *KV capacity* (linear in batch). A product org would ask for the 14B chiplet count and the RRAM program time. Neither is in the paper.

## Master Class

1. **The Real Abstract** — A 7 nm-modeled chiplet mesh from the NUS Fong group (same fabric as LEAP) that puts frozen weights in analog RRAM, LoRA in SRAM-CIM, attention-like DMACs in mesh routers, and KV in a three-tier scratch/SRAM/eDRAM waterfill. Multi-request means stagger requests across spatially unrolled layers so one RRAM copy is busy more often. Simulator tokens/s and tokens/J vs. an H100 nameplate on Mistral-7B-INT8 at 4k context, batch 1 and 4.

2. **The Rashomon Synthesis** — Microarch and industry agree the *new boxes* vs. LEAP are eDRAM, UCIe, SRAM-DCIM-as-LoRA, and power gating — then split on whether those boxes are circuits or citations. Workload and simulation agree the interesting measured effect is “LoRA steals SRAM → KV hits eDRAM → throughput falls to ~0.71× at B=1, recovers at B=4” (Table IV, p.9) — then split on whether Table V’s 27× vs. H100 is even the same workload. The core tension: the paper’s title claims a *serving* architecture; the graphs are a closed batch of identical 4k/4k requests on a LEAP-derived ISA simulator. Microarch is happiest in Fig. 3; workload is happiest in Fig. 7; nobody should be happy in Table V.

3. **The Magic Trick** — Unroll the model in space (one layer, one cluster), keep one RRAM copy, and turn batch into pipeline occupancy; when SRAM is not holding LoRA, pretend it is a KV cache.

4. **The Skeleton in the Closet** — Spatial mapping is LEAP/PRIMAL (p.6). Simulator is the same group’s instruction model (p.7). No accuracy. No MoE. No chiplet count for 14B. Analog RRAM and IGZO eDRAM are literature macros. H100 350 W vs. 30.7 W (Table V). Exclusive stages cap utilization at batch / depth (Fig. 7). “Cycle-accurate” is ISA-level (p.7).

5. **可提取的问题线索**

1. Decode emits 1 new token per active request per step while prefill is matrix-matrix; a prefill-sized engine sits idle in decode, and a long-context decode engine wastes static power on short prompts. (p.1)
2. KV capacity is `B · T · L · (2 N_KV d_head) · b_KV / 8` bytes; on Llama 3.2-1B, Fig. 2 already reaches on the order of 10² MiB as context goes 4k→16k and batch 1→4. (p.2)
3. Raising batch to recover decode utilization multiplies the volatile KV that must be retained, not just the compute. (p.1–2)
4. Analog nonvolatile arrays are a poor store for runtime intermediates: write endurance and write energy rule them out for KV and activations. (p.1)
5. Throughput via weight replication scales RRAM capacity, chiplet count, area, and leakage approximately linearly with the replica factor, even though every request reads the same pretrained weights. (p.2)
6. SRAM-only on-chip KV hits a capacity wall as `T` and `B` grow; the required store can exceed local memory. (p.2)
7. LoRA adds a second parameter class that must be rewritten when the task changes, while base weights stay frozen — one memory technology does not match both, and adapter-sized SRAM sits unused in base mode. (p.2–3)
8. Table I: prior CIM designs typically fix context, assign memory one role, or run a single batch; LoRA support and dynamic KV scaling almost never appear in the same design as multi-request serving. (p.3)
