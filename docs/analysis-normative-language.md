# normative_language 对照论文分析

- **仓库：** [github.com/lukebest/normative_language](https://github.com/lukebest/normative_language)
- **形态：** 提案文档 v0.1（`normative_language.md` / `normative_language_cn.md` + PDF），**非可运行代码**
- **对照论文：** [arXiv:2604.03312](https://arxiv.org/abs/2604.03312)
- **结论：** **高相关**——补 Idea Factory 的「问题 / 约束 / 裁判」层，正对论文「稀缺的是问题表述」主张。

---

## 1. 仓库是什么

提出 **NDF（Normative Description Format）**：在 Markdown + Git 上组织复杂系统的**规范性描述**（系统 shall / must not / may 做什么），供人类与 AI agent 共同消费。

核心痛点（文档 §1.3）：

> Agent 设计时真正规范 = 背景文档 + 初稿 + 整段 prompt 纠正序列；该聚合体不集中、不可重放、常丢失。

NDF 目标：增量构建、全程修订留史、树状组织 + 交叉引用、人机双可读、支撑多周期 agentic 设计/验证循环。

设计哲学：**中间道路**——拒绝纯散文与全盘形式化（ASL/TLA+/Lean）；结构化自然语言 + 代码作为一等公民（可执行参考模型岛屿）。

---

## 2. NDF 要点（与产品相关）

| 概念 | 含义 |
|------|------|
| 条款（clause） | 稳定 ID、规范性关键词、可交叉引用 |
| 精化层 L0–Ln | 从一句话意图到可执行参考模型，层间 `refines` 链接 |
| 决策记录 | 沉淀「为什么」，含从 prompt 蒸馏的决策 |
| 参数/自由度 | `may` / open questions：合法探索空间写进规范，而非藏在聊天里 |
| 摄取管道 | 从人类导向参考文档（标准、ASL 片段等）投影进 NDF |

工具链在文档中为规划态（lint、链接校验、摄取助手等），仓库本身几乎只有规范提案。

---

## 3. 与论文模块映射

| 论文模块 | NDF 作用 | 判断 |
|---------|---------|------|
| 问题工厂 / 约束定义 | 条款化目标、非目标、PPA/负载约束、开放问题 | **强相关** |
| Generation 输入 | 给 agent 的 canonical 工作指令（引用条款 ID） | **强相关** |
| Evaluation 裁判 | 验收标准与参考模型挂靠条款，失败可归因 | **强相关** |
| Feedback / 遥测 | 可记录校准假设与决策；不采集遥测 | 间接 |
| Gauntlet / OpenEvolve | 上游「宪法」；不替代执行引擎 | **互补** |

论文主张：竞争优势从点子转向「评估基建 + 问题定义」。NDF 把后者变成 **lifetime 版本化工件**，避免工厂自我漂移。

---

## 4. 局限

1. 目前几乎只有提案，无落地工具。  
2. 不生成架构点子，不跑仿真或进化搜索。  
3. 需与 Gauntlet（出题/评审）、OpenEvolve（实现搜索）、电路优化环（落地）显式对接，否则易停留在文档规范。

---

## 5. 对 ArchZero 产品的建议

| 优先级 | 动作 |
|--------|------|
| P0 | 用 NDF 思想先做**轻量问题包**：目标、约束、验收、开放自由度、决策日志（哪怕目录约定即可） |
| P1 | Candidate / 评估失败原因引用条款 ID，便于归因与回灌 |
| P2 | 再补 lint、摄取、查询工具链 |

---

## 6. 一句话

**NDF = Idea Factory 的规范与裁判层；没有它，自动化探索容易「做出东西却丢了支配设计的圣经」。**
